# Week 4 troubleshooting

Seventy-three situations the closed loop can run into, in the order they tend to appear.
Each row says what to check first, and what this implementation actually does —
the second column matters, because a diagnostic guide that describes behaviour the
code does not have is worse than none.

Symptoms are grouped by where they surface: connection, model, perception,
resolution, execution, verification, recording.

## Connection

| Symptom | Check first | What this code does |
| --- | --- | --- |
| `Connection refused` / no response | IP, port, that the service is listening, that both machines are on the same subnet, firewall rule | `ModelError` with the endpoint in the message. The run is `blocked`, never `failed` — nothing was attempted |
| Service reachable, `--health-check` passes, but the model never sees the screen | Send a request **with** an image; check the model name and that it is a vision model | A text-only success is not evidence of vision. `ObservationService` always passes `image_path` from the captured frame |
| A long pause before the first reply | Whether the model is loaded (`ollama ps`), free system memory, how many other things are competing for it | First call loads the model. Warm the endpoint before a task; see the Windows manual step 5 |
| Requests are slow, or a timeout is suspected | Cold or warm state, free memory, concurrency, and how many retry layers are stacked | `model.timeout_seconds` is a **per-request** limit, not a task budget. Week 3 measured 8-10 s cold with memory free and about 72 s with it exhausted, and the slow part was the vision encoder paging, not model loading. A 72 s success obtained with a long probe timeout does **not** prove the default client would have timed out either - measure it through the client before drawing a conclusion. `scripts/week4_warmup.py` is that measurement: it probes text and then a real screenshot through the project's own client and records cold/warm state, free memory, per-request time, the classified failure and the retry count. Run it before the tasks so the cold number is recorded once, separately, instead of landing inside the first task's timing |

The endpoint is read from `GUI_AGENT_BASE_URL` or `--base-url`. A missing API key is
reported before any network call, so a connection error is never a credential error
in disguise.

## Model

| Symptom | Check first | What this code does |
| --- | --- | --- |
| HTTP 500 | Service log, model and memory state, the request body | Reported as `ModelError` with the underlying exception name. **Kept separate from a timeout and from a truncated reply** — the three have different causes |
| A failing request takes about three times its `timeout_seconds` | The SDK's own retry policy as well as `model.max_retries` | The SDK is given `model.max_retries` now, so `0` means one attempt rather than one attempt plus two the SDK added on its own. `model_requests` counts what actually left the process |
| `400 ... request (N tokens) exceeds the available context size (M tokens)` | The actual loaded context in `/api/ps` against request size. A 2560x1600 screenshot plus the former 60-slot list measured 7 517 tokens; 4096 was insufficient. The larger target list and comparison images need a new measurement | `blocked` before any action. Raise the server/model context before starting, or lower `execution.max_elements`. Historical runs used 16384; the latest T04 preparation verified actual loaded context 32768. Setting a shell variable after the server has loaded its model is not proof that the running context changed. The task runtime does not adjust it |
| `... N further elements omitted to fit the prompt` | How much text is on screen, and `execution.max_elements` | Not an error. The element list is trimmed one **whole** element at a time — an id with half its text would be unusable — and the prompt says how many were dropped. Raise `execution.max_elements` or the server's context window to keep more |
| Reply truncated mid-JSON | Finish reason, response length, **prompt length**, number of steps | `PlanParseError`; the planner retries the format once, then reports `blocked`. A partial plan is never executed |
| Plan is valid JSON but the steps do not fit the screen | Whether the prompt carried the element list | The adapter refuses at resolution time; nothing is clicked |
| **A T04 plan names a sidebar contour as `发送` while the real send label is listed** | The scope of `visible_text`, actual candidate boxes and typing arguments; a valid JSON plan can still point at the wrong region | A saved-frame 300-element plan cost 21 806 prompt tokens and selected the wrong contour. T04 planning now lists only observed candidates within the independently authorised composer, supplies exact marker typing arguments and tells retries that text was already typed. The production-context real-model probe returns click-editor, type-marker, click the real send OCR candidate using 5 841 prompt tokens, with no dispatch. Current-candidate grounding, recipient/header/focus checks, cumulative limits, confirmations and fail-safe still govern execution; the probe is not a real sent-message result |
| `duplicate step_id` / `... is finish but N step(s) follow it` | The plan's step ids, and where `finish` sits | The plan is rejected at parse time and never executed. A step after the terminal step would otherwise be dispatched, because executability looks only at the verb |
| `the plan reports errors and will not be executed` | What the model put in the plan's `errors` list | `blocked` before any action. The model uses that field to say it could not work the task out, and running it would read "I am not sure" as "go ahead" |
| `no element matches '...'` | Take a fresh screenshot; check the OCR language and threshold; is the page still loading? **And: is the step's target text anywhere in the frame's element list at all?** | The step fails and ends the current plan pass; bounded re-planning may try again from a fresh observation. It does **not** click a default position, and it does not retry with a guessed target. If the text is absent from the list, the problem is the frame, not the model - see the row below |
| The model aims at text that is nowhere on screen (`'browser'`, `'browser icon'`, `'week4 test application'`) | **What window the capture actually contained.** Read `obs-0001.json` and look at the element texts: if they are sentences from a terminal, a log, an editor or a chat panel, the frame was that window, not the desktop | Not a model fault. This is the failure the Windows review produced three times, and the mechanism is worth knowing: `ObservationService` ranks text above contour boxes and then cuts the list at `execution.max_elements` (60 in the cited run; 300 after the anonymous-box repair). Under that former cap, one maximised text-heavy window consumed the entire element budget, and the icons and shortcuts the task needs never reach the prompt. The model is asked to open a browser it was never shown, so it names the most plausible text instead - a correct response to a bad frame. Measured here: a console window produced 145 text elements whose top entries were `'not set.'`, `'(825.4 ms'`, `'Cache hit 99%'`, `'blocked'`; with that gone the same screen yields desktop icons instead. **The agent's own window is the usual culprit**, because it is always there while the agent runs, and it cannot be closed from inside the run. `scripts/week4_preflight.py` checks for this before a case starts: it captures a frame, counts the text elements and fails with this explanation rather than letting a doomed run proceed. Fix by running the case from a session whose window is not on the captured monitor, or by minimising everything first |
| `... is not from observation ... and the step names no text target` | Whether the target is labelled, or a detected anonymous control with trustworthy old and current pixels | The adapter still rejects a bare stale id. The runner can first refresh an anonymous id by unique pixel/context correspondence with an actual current candidate. A changed control permits one constrained visual mapping request, followed by a new capture and pixel confirmation. Missing/ambiguous evidence stops the pass; labelled targets retain unique text rebinding. No old coordinate or nearest box is a fallback |

## Perception

| Symptom | Check first | What this code does |
| --- | --- | --- |
| `monitor_index 1 is out of range (available 1..0)` | Two causes, and the fix for one does nothing for the other. **Asleep or locked display** - wake it and re-run. **The process cannot see the screen at all**, which on macOS means the terminal running the command has no Screen Recording permission | The run is `blocked` with that message, dispatches nothing, and exits 2 - it does not crash. `available 1..0` is the tell: only the aggregate pseudo-monitor at index 0 exists and it measures 0x0, i.e. no display is visible to this process. Waking the screen does not fix that; grant the terminal Screen Recording permission in System Settings -> Privacy & Security and restart it. A remote session reports the same thing, since there is no local display to capture |
| **A run driven from inside a chat or IDE window clicks that window's own text** | What is on the captured monitor. Read `obs-*.json`: if the element texts are the agent's own conversation, log or panel, the target application was never in the frame | Not a model fault, and it is the hardest one to see. Measured here: a driver double-clicked the text *"verification failed again after the double-click on the Microsoft Edge icon at coordinates (2473,400)"* - its own conversation, which contained the string it was told to find. The step reported `resolved=True` and `verification: passed`, because it really did click what the frame offered. **The agent's own window cannot be closed from inside the run** (it is how the run is being observed), and hiding the console is not enough: creating any console takes the foreground, so the target application ends up behind the desktop and the capture returns icons. Tried and insufficient: minimising the console, `SW_HIDE`, moving it to `-4000`, launching the driver windowless with `CREATE_NO_WINDOW`, and re-asserting the target's foreground for 75 s. **Fix by separating the two**: observe the run from another machine or device (an SSH session, a headless client), or run the case from a session whose own window is not on the captured monitor. This machine has no second monitor, so there is no local arrangement that works |
| **A case observes the desktop even though its target application is running** | The window's **minimised** state, not its existence: `IsIconic` on the handle. Then check whether anything is putting the target back | Two effects combine here, and both were measured. (1) **Minimising any window activates it in z-order terms, and the next window down is the desktop** - so a driver that minimises its own console to keep it out of the frame simultaneously pushes the case's target behind the desktop, and the capture returns icons. (2) **Focusing the console cancels the minimise.** A launcher that reported its console handle *and then* called `SetForegroundWindow` on it undid the driver's minimise a fraction of a second later, which is why the code looked right and the frames kept showing the desktop. Restoring the target *after* the minimise is what works, and it only works once nothing re-focuses the console. `IsIconic` is the diagnostic: a target found at `(-21333,-21333)` with `IsIconic=True` was never going to be in the frame, and `SetForegroundWindow` alone does not bring such a window forward - `ShowWindow(SW_RESTORE)` has to come first |
| **The tool that puts a window in front is itself the thing taking the foreground** | Sample who owns the foreground *during* the run, not before it: `GetForegroundWindow` plus `GetWindowTextW` and `GetClassNameW`, one line per half second | Found by doing exactly that, after four rounds of inferring and three wrong fixes. A driver that looked up the browser's handle by shelling out to PowerShell logged **347 samples with `powershell.exe` in front against 104 with Chrome** - the function whose job was to keep the browser forward was spawning the window that pushed it back. Enumerating top-level windows in-process (`EnumWindows` filtered by `Chrome_WidgetWin_1`) removed the competing window: the same run then logged **658 of 658 samples with Chrome in front**. The general rule this is an instance of: any helper invoked from the observing process can appear in the capture, and a subprocess that creates a window is the least obvious and most frequent case |
| **A step fails to find text that the last frame clearly showed** | Whether the step is resolving against a *later* frame than the one the plan was written from - the failure names its own observation (`in obs-0002`), and the plan's was `obs-0001` | Measured on T02: the model named '搜索或输入 Web 地址' - the real placeholder of Chrome's search box, read from the frame the plan was written against - and the step then failed because it resolved against `obs-0002`, where the window was no longer in front. Nothing was wrong with the element list: the browser's own text was in the planning frame at indices 17, 23, 47, 48, 50 and 51 of 60, so the cap was not the cause either. The rule this is an instance of: `_locate` deliberately resolves against the current frame so a stale plan cannot click through a changed screen, which means **every step needs its target present in the frame after it, and a window that loses the foreground between steps cannot supply one** |
| **The foreground sampling shows a modal dialog, not the application** | The foreground log's own text, not the window count: `'要恢复页面吗？'` appeared in 205 of 442 samples of one T02 run while Chrome was in front in the other 237 | The dialog is the browser's "Restore pages?" prompt, and it is a consequence of the harness rather than of the case: repeatedly killing a browser to satisfy a precondition leaves an unclean exit, and the next launch offers to restore. It is modal, so it covers the page the case is about, and a click meant for the page can land on it. Both incidents in this project's history have this shape - the earlier one was Edge's `'Microsoft Edge 意外关闭。'` banner sitting over the address bar the rule looked for. Clear the session files before the run, or start the browser with the flags that suppress the prompt; do not read the sampling as "the application was in front" without reading its text too |
| **`2 elements match 'x'; refusing to pick one arbitrarily`** | How many times the text appears, and where. The message lists each candidate with its id, so the frame answers it | Correct behaviour, not a failure - and worth reading before "fixing" it. Measured: a run against a blank page aimed at `'about:blank'`, which a blank page shows twice (the omnibox and the page's own label), and the adapter refused rather than guessing. The same guard caught `'msedge'` twice and `'x'` five times in earlier rounds, and every one of those was a plan that named a string the screen genuinely carried more than once. **Prefer an `element_id`**: ids are unique by construction, which is why the prompt asks for one, and a step that gives both an id and a text is re-bound automatically when the id is stale |
| **The capture shows a different window of the same application** | Which window the driver put back, not only which application. `CabinetWClass` covered six windows on this machine and `Chrome_WidgetWin_1` covers every Chromium window including other applications' | Found with T03, whose screen is a folder: the capture kept showing "此电脑" or GitHub Desktop while the model aimed at `'week4 test'`, and the restore had been written for browsers only. The fix has two halves and the second is the one that is easy to miss - the target has to be chosen by class **and** title fragment (six `CabinetWClass` windows, one of them the right folder), and the restore has to happen **after** the console is minimised, because minimising activates the next window in z-order and that is the desktop. A restore that runs first is undone by the minimise that follows it, which is exactly how this failed after the first half was in place |
| **A close action succeeds and the window is still there** | Whether the application is tabbed. Read the window title and the process id before and after, not the action's own verdict | Measured on T05: the plan was `hotkey alt+f4`, the adapter resolved it to `["alt","f4"]`, it reported `success: true`, and the foreground sampling was 381 of 381 samples with Notepad in front - so the keystroke reached the intended window. Notepad was still running afterwards with its title unchanged. Windows 11's Notepad is **tabbed and single-process**: closing a tab does not end the process, a second launch reuses the running one, and the marker text the rule watches for stays on screen in another tab. Confirmed directly - `Alt+F4` on a blank Notepad left pid 64740 alive and only renamed its window to '无标题'. For a rule that asks for a window or a process to be gone, the application must not be one that closes per tab |
| **A close action reports success and the window is in a save dialog** | Whether the document was dirty when the run started. The dialog is modal and its own text names the file, so the capture answers it | Measured on T05 and then reproduced directly. The run's own record read `keys=['alt','f4'] note='alt+f4' success=True`, and Notepad was still open afterwards. Sending the same keys by hand to a dirty document produced the dialog - `'是否要将更改保存到C:\...\week4_sample.txt?'` with `保存 / 不保存 / 取消` - which is what absorbed the close. Sending them to a **clean** document closed the window immediately: the foreground moved from `'week4_sample.txt - Notepad'` to the next Notepad window and the target window was gone. The file had been dirtied by an earlier synthetic-input experiment on this machine, so the case's own precondition ("the marker text is on screen") was satisfied while the state the close needs was not. A close case needs the document saved as a precondition, not only opened |
| **`the success rule already holds on the untouched screen ... this run cannot be credited with it`** | Nothing is wrong - this is the guard that stops a "something must be gone" case being credited for a window it never closed. Read it as "the precondition is not in the frame", and check the capture | The rule for T05 is that a marker has to leave the screen, and a screen that never showed it satisfies the rule while proving nothing: a run that closes nothing would pass. The guard evaluates the rules against the **first** frame and blocks, with `actions: 0` and no verdict, when they already hold. Measured on T05_20261004_175250: `status = blocked`, `actions = 0`, and Notepad was still running with the file open - correctly not counted as a success. The cause of the first frame lacking the marker was the same window-restore race as T03: the console's minimise moved the foreground and the capture showed a folder window instead of the editor. So the note means "the target never reached the frame", and the fix is on the capture side, not the rule side |
| **Typed Latin text arrives with Chinese characters in it** | The machine's input method, not the model and not the OCR. `'GUI agent research'` in the records is the tell | Measured directly: with Microsoft Pinyin active, sending the Latin string `GUI agent research` produced **`GUI阿根廷research`** in the field - the IME converted `agent`. The same mechanism explains every odd string this project recorded and had attributed elsewhere: `'researchGUI阿根廷researchresearchGUlresearch'` (read as accumulated typing), `'guivant'` and `'阿根廷文'` (read as OCR noise). Switching the machine to English with Shift made the identical action reach a real results page - `google.com/search?q=GUI+agent+research` - so the plan, the coordinates and the input path were all correct. **A program typing Latin text into a machine with a CJK input method active does not get the characters it sent.** For a browser there is no in-process fix: Chrome returns 0 from `ImmGetContext` (it uses TSF and composes input itself), so an IMM32 call cannot reach it, and calling one before typing there produced no text at all. The remedy is an operator step - leave the input method on English before the run - which is why `control/actions.py` documents the helper without wiring it in |
| **A run reaches the goal and the rule still fails** | Whether the rule's marker is a string the OCR engine can actually read back. Re-read the frame: the evidence is usually visible to a person and absent from the element list | Measured on T02 after the search was submitted successfully. The frame is a real Google results page - `google.com/search?q=GUI+agent+research&oq=...&gs_lcrp=EgZjaHJvbWUyBggAEEUYOTIGCAEQABg...`, a tab titled `GUI agent research - Google`, an AI overview and arXiv results - and the run was recorded `failed` with `expected on screen but not found: google.com/search`. The element list for that same frame does not contain the string: the URL is long, sits in a narrow field, and the engine did not read it. Two things follow. **A short stable marker beats a precise one**: `google.com` was read on the results frame where `google.com/search?...` was not, so the rule uses the host. **And OCR of a browser's address field is not reliable enough to be the sole evidence for "a page loaded"** - the same rule read the host on one frame of a run and not on the next frame of that same run, which is why this remains a known limit of measuring T02 on this machine rather than a solved step |
| **No marker can settle a case whose evidence lives in a browser's chrome** | Whether every candidate signal goes through the same reader. If they do, more markers do not add reliability - they add chances for the same reader to miss | Established on T02 by measuring three candidate results-page signals against three frames. On the frame that really was a Google results page, the tab title `'GUI agent research - Google ×'` was read and `google.com` was read, while the element list held no `google.com/search...`. On the **next frame of that same run** the reverse: the query text was read and neither the title nor the host was, although a person can see the tab and the URL in both frames. And on the frame that had falsely passed, the query was read and nothing else - so the one signal that survived every frame is the one that cannot tell a submitted search from text waiting in an address bar. Three markers, each missing on some frame, none sufficient. The conclusion is about the measurement, not the case: **when the only evidence for "the goal was reached" is text inside browser chrome, OCR reliability sets the ceiling on what can be concluded**, and an operator should read the frame. A different screen size, a different engine, or a rule that uses the window title through the accessibility API rather than through OCR would each change it |
| **The same prompt yields one step on one run and nine on the next** | Nothing is broken - this is the model, and it is worth knowing before spending a round on prompt wording | T02 asks for a search, which needs two actions, and the plan length for the identical prompt and frame has been measured at **1, 2, 8 and 9 steps** across runs. The rule that says a plan may hold several steps is present, first in the list, and has been reworded twice - "Plan to the goal", then "Plan every step to the goal and do not stop short" - and four consecutive calls with the stronger wording returned **one step each**, all of them a bare `click`. So wording is not the lever here, and position is not either: the rule already sat first. What follows is a planning budget, not a prompt edit - a run that needs two actions succeeds when the model happens to emit them, and the fix for a case that must be reliable is a model that plans multi-step consistently, or a harness that re-plans after a single action. The former runner called `planner.plan` only once per run, so an incomplete one-step plan ended without reaching the goal. The current runner adds bounded planning passes from fresh observations when a plan falls short or cannot resolve a step: `max_planning_attempts` defaults to 4 and shares the wall-clock budget. It does not call the model after every successful action. This recovery addresses the measured incomplete-plan failure; the retained successful `T02_20261004_210409` itself records one planning attempt and one model request |

## Resolution

| Symptom | Check first | What this code does |
| --- | --- | --- |
| `N elements match '...'` | Element ids, whether a region or context could disambiguate | The run stops and lists the candidates. **It never takes the first match** |
| `no element matches '...'` although the label is plainly on screen | Whether the backend returned words instead of lines — check the element texts in the observation JSON | Tesseract rows are merged back into lines, so `Summary (required)` is one element. If a phrase still spans two elements, the adapter matches the query's tokens against a run of neighbouring elements and refuses when more than one run matches |
| `N element runs match '...'` | How many places on screen carry that phrase | The run stops and lists the runs, same policy as an ambiguous single element |
| `scroll_amount must be a number` / `duration must be a number` | What the plan put in the argument | `ActionResolutionError`, so the run records a failed step. A bare `ValueError` here would have escaped the runner entirely and ended the run as a traceback |
| A dry run fails with `no element matches '...'` while you are using the computer | Whether the desktop changed between the two observations | Correct, and not a defect: the plan is written from one frame and every step is re-resolved against the next, so a target that scrolled away, closed or was covered is refused. Run the dry runs on a desktop you are not touching |
| The screen sleeps between the last action and the verdict | Whether the display went off | `inconclusive`, with `could not look at the screen to verify` as the reason. Nothing is claimed either way — a screen nobody can look at is not a passed task *or* a failed one |
| A step resolves to a point outside the monitor | The screenshot size against the control size | `ActionResolutionError`; the point is refused, not clamped to the edge |
| `key '...' is not in the allowed key set` | The key name the plan used | Only a fixed key list is accepted. This is deliberate: the model must not be able to drive a shell through `type_text` or `key_press` |

## Execution

| Symptom | Check first | What this code does |
| --- | --- | --- |
| Text lands in the wrong field | The target's current candidate, foreground identity and, for T04, the active conversation header | Fresh resolution and executor checks remain required. T04 visually authorises the recipient and empty composer before planning, preserves the same header pixels before every input, checks focus immediately before dispatch and types only the approved fresh marker. Unknown/changed evidence refuses input. The final check-to-input race still exists; these guards do not prove every character reached the intended field |
| Typing does not submit | Whether the plan contains the submit step, and what it defines as the trigger | A draft is not success. T02 requires the results page, not text in the box |
| Chinese or other non-ASCII input fails | `pyautogui.typewrite` and the current input method | Not supported and not claimed. `type_text` is ASCII-only; a clipboard-based path would need its own dependency and tests |
| The model presses something destructive | The plan, and the task's risk level | `medium` and `high` tasks ask for a second, separate confirmation, and it prints the text the plan will actually type. The risk policy is in the runner, so a caller cannot drop the prompt. There is no `--yes` |
| `--execute needs an interactive terminal` | Whether stdin is a terminal | `blocked`, exit code 2, before anything is captured. With nobody to ask, consent is not assumed. Run it from a terminal, or leave `--execute` off for a dry run |

## When recording a real problem

Record the reproduce command, the commit, the config, the steps, expected against
actual, the evidence path, the change and the regression result. "Improved the model
behaviour" is not a record.
